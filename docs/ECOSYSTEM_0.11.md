# Saga 0.11 package and third-party ecosystem

## Native Saga packages

`publish`, `search`, `add`, and `pkg:` imports form the reference package workflow. Packages are canonical `.sagapkg` files with fixed versions and SHA-256 verification.

Publisher signing:

```bash
saga registry keygen --private publisher.pem --public publisher.pub.pem
saga publish . --registry https://registry.example --signing-key publisher.pem
```

The reference registry validates Ed25519 signatures when supplied and returns the publisher fingerprint to installers.

## Python ecosystem bridge

A plugin can include `plugin.saga-plugin.json`:

```json
{"imports":{"numpy":["mean"]}}
```

The plugin source receives a facade named `numpy` containing only `mean`; `import` statements remain forbidden. On Linux, installed package roots are bind-mounted read-only into the plugin's private mount/network/PID namespace. Values cross a serialized Saga boundary; arbitrary Python object identity is rejected.

This makes existing Python packages usable as explicitly trusted dependencies without turning the Saga process into a Python `import` shell.

## WebAssembly component bridge

The ecosystem SDK generates a WIT contract template for Component Model libraries. Saga's current executable WASM compiler target is a WASI Preview 1 module; WIT package bridges are a separate interoperability surface and should not be described as Component binaries generated by the Standard compiler.

## Public registry status

The repository includes a network registry protocol/server and container deployment template. Operating a public Internet registry additionally requires production TLS, identity/account recovery, abuse response, rate limiting, backups, monitoring and governance. Those operational facts cannot be created merely by shipping source code.
